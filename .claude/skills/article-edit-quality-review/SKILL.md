# Article Edit Quality Review

## Overview

記事修正時に、局所最適な差し替えで記事全体の読み味を壊さないためのレビューを行う。
修正箇所の正しさだけでなく、読者が冒頭から最後まで自然に読めるか、記事で伝えたい内容が弱まっていないかを確認する。

## Workflow

1. 対象記事のfront matter、冒頭、TL;DR、該当修正箇所、前後の見出しを読む。
2. 必要に応じて記事全体を通読し、変更箇所が全体の流れに与える影響を確認する。
3. 下記チェックリストで、修正箇所と記事全体の両方を確認する。
4. 問題があれば、該当箇所だけでなく周辺文脈も含めて最小限修正する。
5. 修正後に冒頭から該当セクションまでを再読し、重複や矛盾が残っていないか確認する。
6. 報告時は、変更内容に加えて読者体験・冗長さ・誤解リスクの確認結果を簡潔に伝える。

## Checklist

### Reader Flow

- 冒頭が注意書きや前置きに寄りすぎず、読む勢いを止めていないか。
- 導入、TL;DR、本文の順番に自然な役割分担があるか。
- 重要な結果や問いにたどり着く前に、読者を選別しすぎていないか。

### Redundancy

- 直前・直後の段落、TL;DR、見出し、メッセージボックスと同じことを繰り返していないか。
- 同じ説明を残す場合、それぞれの粒度や役割が違うか。
- 「測った」「換算した」「共有する」など、記事の基本説明が複数箇所で過剰に反復されていないか。

### Message And Warning Boxes

- `:::message` は読者の理解を助ける位置にあるか。
- 注意書きが必要な場合でも、本文を読む動機を削いでいないか。
- 公式ではない、条件依存である、参考値である、といった免責は結果理解に必要な場所へ置く。

### Main Point

- 記事で一番伝えたい内容が、修正によって弱くなっていないか。
- タイトル、導入、TL;DR、本文が同じ結論を支えているか。
- 読者がこの記事を読み終えたときに持ち帰る内容が明確か。

### Misunderstanding Risk

- 数字、対象プラン、モデル、計測時刻、前提条件、推定であることが誤解されないか。
- 公式仕様・実請求額・個人の観測値の区別が曖昧になっていないか。
- 断定しすぎる表現がある場合、根拠と条件が本文内にあるか。

### Tone

- 読者に押しつける表現ではなく、実測や経験を共有するトーンになっているか。
- 「誰向けか」を書く場合、読者を狭めすぎたり、読む前に離脱させたりしないか。
- 謙虚さを保ちつつ、結論がぼやけていないか。

## Output

通常の修正報告に加えて、必要に応じて次のように短く添える。

- 「冒頭はフック、TL;DRは要約に役割を分けました」
- 「前後段落との重複が残っていないことを確認しました」
- 「推定値であることと計測条件はalert側に残し、冒頭の読み出しを軽くしました」
